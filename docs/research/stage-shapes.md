# 30 个实验各自的主干（以及抽不出主干的那些长什么样）

> 2026-08-18。为 `tasks.md` 的 **0-1** 排雷：主干式布局到底能覆盖几个实验。
> 逐个过了 `registry.ts` 的页签与读数，拿不准的开了 `stages/*.tsx` 看结构。
>
> **结论先说：30 个里只有 10 个有真主干。0-1 原来的样板（Cache）和 mockup（数据包封装）
> 恰好都是这一类 —— 也就是说，那两个样板一个雷都没排到。**

---

## 判据

**主干** = 一条从左到右的流水：同一份数据依次流过几个**性质不同**的加工段，
每段能挂上它自己的旋钮和读数。

不满足的有两种，各自是另一种舞台形态，不是"做得不好"：

- **时空图**：横轴已经给了时间/周期/轮次，纵轴是实体。横轴被占了，摆不下主干。
- **就地演化**：只有一个结构（树/表/图/数组/内存条）随步骤变形，数据没有"流过"任何地方。

---

## 甲 · 真主干（10 个）

| 实验 | 主干 |
|---|---|
| **cache** | 地址 → 拆位域(tag/组号/偏移) → 定组 → 比 tag → 命中/缺失 → 淘汰 |
| **vm** | 虚地址 → 拆(虚页号/页内偏移) → 查 TLB → 查页表 → 缺页? → 物理地址 |
| **float** | 十进制数 → 定符号 → 转二进制 → 规格化 → 定阶码 → 截尾数 → 舍入 → 组装 |
| **crc** | 数据 → 补 r 个 0 → 模 2 长除逐位 → 余数 → 拼成码字 |
| **hamming** | 数据位 → 算校验位数 → 按 2^k 布位 → 分组求校验 → 码字 →(出错)→ 校验子 → 定位纠正 |
| **subnet** | IP + 掩码 → 拆二进制 → 按位与 → 网络号 → 与路由表逐条比 → 最长前缀 |
| **inode** | 逻辑块号 → 落在直接/一级/二级/三级 → 逐级查索引块 → 磁盘访问次数（`inchain` 已经是链） |
| **bitmap** | 盘块号 ↔ 字号/位号 → 换算 → 置位/清位（`bmcalc` 那半边是流水，`bmgrid` 那半边不是） |
| **multiply** | 被乘数/乘数 → 判断位 → 加或减 → 移位 → 下一轮 → 积（寄存器逐轮推进） |
| **kmp** | 模式串 → 求 next 表 → 双指针在主串上走（两段，第二段是就地演化，**算半个**） |

**九个半，凑整算 10。** 都集中在计算机组成原理与计算机网络 ——
因为这两门课的题目本来就长这样：**给一串位，按规则拆开、逐段加工**。

## 乙 · 时空图（7 个）

横轴已经是时间，主干无处可摆。它们已经是对的形态，缺的不是主干，是**竖光标 + 旁白**。

| 实验 | 横轴 | 纵轴 |
|---|---|---|
| **scheduler** | 时刻 t | 进程（甘特图） |
| **pipeline** | 时钟周期 | 指令（时空图） |
| **arq** | 时间 | 发送方 / 信道 / 接收方 |
| **handshake** | 时间 | 客户端 / 服务器 |
| **csma** | 时隙 | 各站点 |
| **semaphore** | 时间 | 生产者 / 缓冲区 / 消费者 |
| **tcp** | 轮次 | cwnd（是曲线，不是流水） |

## 丙 · 就地演化（13 个）

一个结构居中，每一步动它一下。硬套主干只会把"一棵树"切成假的几段。

| 实验 | 那个结构 |
|---|---|
| **avl** | 一棵树（旋转） |
| **bplus** | 一棵树（分裂） |
| **huffman** | 一片森林合并成一棵树 |
| **sort** | 一个数组（逐趟） |
| **hash** | 一张表（逐个装入 + 探查） |
| **dijkstra** | 一张图 + 距离表 |
| **mst** | 一张图 + 已选边 |
| **topo** | 一张图 + 拓扑序 |
| **traverse** | 一张图 + 栈/队列 |
| **banker** | 一组矩阵 + 安全序列搜索 |
| **page** | 物理块表（逐次替换） |
| **disk** | 磁头轨迹折线 |
| **partition** | 一条内存条带（`memaxis`） |

## 所以 0-1 要改什么

**原来的判断错了一半。** 我把提案叫「主干式布局」，但主干只是**甲类的舞台形态**。
真正能覆盖 30 个的是**壳**，那才是通用的三条：

| 通用的（30/30） | 现状 |
|---|---|
| 目录收成下拉，不占一列 | 占 178px 常驻 |
| **控件贴着它作用的对象**（不只是"贴主干" —— 丙类是贴那个结构，乙类是贴那条轴） | 参数全挤在右列 236px |
| 目标条常驻在舞台上方 | 挤在页眉 chip 里 |

舞台形态则**分三种**，各要一个样板：

| 形态 | 数量 | 样板候选 | 旋钮贴哪 | 读数贴哪 |
|---|---|---|---|---|
| 甲 · 流水 | 10 | Cache（已有 mockup） | 它作用的那一段 | 它产生的那一段 |
| 乙 · 时空图 | 7 | 进程调度甘特图 | 轴的上方（算法/时间片） | 竖光标旁的旁白 |
| 丙 · 就地演化 | 13 | 散列表 或 AVL | 结构的外框上 | 结构旁边「这一步动了谁」 |

**丙类是最大的一类（13 个），也是最没想清楚的一类。**
它的难点在于：一个结构居中之后，屏幕两边空出来的地方放什么？
如果答案是"还是放参数面板和读数面板"，那丙类等于没改，只是把两列挪近了一点。

---

## 给 0-1 的建议

1. **样板从 1 个改成 3 个**，每类一个。工作量不是三倍 —— 壳是共用的，多出来的是两种舞台的排布。
2. **先做丙类**，不要先做甲类。甲类已经有 mockup、已经知道能成；丙类是 13 个实验的命运，
   而且它是唯一一个**可能做不出比现在更好的形态**的。先做最可能失败的那个。
3. **接受一个可能的结果**：如果丙类想不出更好的，0-1 就只覆盖甲+乙 17 个，
   丙类 13 个保持现在的三列。这不是失败，但要现在就认，别做到一半才发现。

## 未决

- 甲类里 **kmp** 和 **bitmap** 是"一半流水一半就地演化"，归哪边取决于舞台怎么排，
  真做的时候可能要拆成两段屏。
- 丙类 13 个里，**图算法四个**（dijkstra / mst / topo / traverse）共用 `GraphView`，
  它们大概率能共用同一种排布 —— 如果成立，丙类的实际形态数会少于 13。没验。
- 这份分类是**看代码结构分的，不是看用户怎么用分的**。真人用起来是不是也这么感知，没验。
