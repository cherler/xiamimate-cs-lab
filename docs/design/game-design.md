## 一、这是什么

一款**"计算机世界可无限下钻"的解谜/建造游戏**。玩家从一个目标(一个完整功能,如"打开网页")出发,把它拆解、搭建、点亮——最终搭出一台**会运转的机器**,请求从机器里跑一个来回,功能达成。

- 内核是**知识**(真实的计算机原理),外壳是**游戏**。
- 教育目的交给 cs-lab;本项目**只要游戏性**,知识是玩法机制、不是教材。
- 同一套玩法可套 DNS / TCP / 缓存 / 进程 / 文件系统 / 数据库——换棵树就是换个关卡。

## 二、核心玩法(两拍)

**① 搭机器(建树 · 拖拽拼装)**
- 开局画布上只有一个根节点(目标)。左侧素材库装全套可拖的块。
- 从根往下拖拽,把整棵**倒长的知识树**建出来:拖对入树、拖错弹回(+咕噜说为啥)。
- 库里只显"当前可放的"(父已入树的),自我引导。
- 一个节点的孩子全拼齐 → 它**点亮**并冒泡点亮父节点 → 组件整枝亮。
- **无限画布**:节点原地展开/收拢/缩放/平移,任何节点可继续下钻。

**② 运行机器(点亮 · 演出)**
- 搭好后运行:一个**请求令牌**从机器里流过,一档档齿轮转起来、逐档通电点亮、令牌逐档变形(域名→IP→装进IP包→加密→网页),末端吐出结果。
- 运行本身 = "请求发出去又返回来" = 关卡目标,既是爽点又是教学动线。

**爽点 = 掌控成长**:从一片灰的机器骨架,被你亲手拖零件拼出来、点亮、连成片、跑起来,越来越强。

## 三、内容模型(层级 + 铁律)

**六层下钻**(默认到"字段"为底,比特/物理为可选深钻):

```
目标(我要做什么) → 组件(谁负责) → 素材(需要什么) → 结构(长什么样) → 字段(每格什么规矩) →〔比特/物理〕
```

判据(怎么归层):能叫出名字的子系统=组件;组件用到的具名部件/机制=素材;部件的内部布局/过程序列(能画成图)=结构;单个具名槽位+取值规则=字段。

**铁律:素材必须是"真东西"**(见 memory `ground-materials-in-real-artifacts`)——抓包/教材里指得到的实体(SYN包/MAC/证书/字段),不是"尽力而为/退避"这类只能描述、指不到实体的抽象性质(那是旁白,不是材料)。定素材的方法:**跟着一次真实请求走一遍,沿途系统真产出了哪些能抓到的东西**,而不是凭概念自由发挥(自由发挥必玄乎、还漏东西——曾漏掉 TLS)。

真源:`game/craft/levels.ts`(教材级"打开网页"树,TLS 补齐,每节点都是真实体)。

## 四、壳 / 美术

- **隐喻:搭一台会运转的机器**(Opus-Magnum / Zachtronics 黄铜蒸汽朋克)。节点不是方框,是有美术的机器模块;边是传动/管道;点亮是一场演出(齿轮转 + 令牌流 + 火花 + 通电辉光)。
- **为什么不是图**:G6/D3/React Flow 都是图表库,产出是「图」不是「游戏」,所以"太普通、展示不出好玩"——引擎从来不是缺的那味,美术隐喻+演出才是。
- **美术**:用生图 API 生成(Opus-Magnum 级黄铜机械件);当前是 procedural 占位。运动/节奏后续慢慢调。

## 五、技术架构

**拆开两件事**:
- **布局(树怎么排)= 解决过的数学** → 用 `d3-hierarchy` 只算坐标(已装 npm 包)。**绝不手写 tidy-tree**(手写必重叠)。
- **好玩(壳)= 美术 + 演出(juice)** → 交给游戏渲染器(Canvas 2D / Pixi / Phaser),把坐标画成会动的机器。

**结论**:图表库(G6/D3/React Flow)出局——它们只会画图。渲染走游戏引擎。

**复用资产**(换渲染层不动):
- `game/craft/levels.ts` — 内容树(真源)。
- `dropNode / bubble` 建树校验+冒泡点亮逻辑 + 冒烟(建树 16✅)。
- `solvers/dns/*`、`solvers/route/*` — 真求解器,当"真源"驱动运行时的真实反馈。
- `scripts/check-graph.mjs` — 反应图不变量校验器(无环/可造/无歧义)。
