# 2026-08-17 · L2 组合级验证

**L2 的定义**：AI 用**已有原语组装**新实验，不只是换参数。

**结论**：**36/36（12 题 × 3 次）= 100%**，选原语和填参数都满分。
另外挖出一个"权威来源"的设计问题。

---

## 一、先建组合原语：`compare`

408 真题里"分别采用 X 和 Y，比较…"是高频题型。这需要一个新原语。

跟已有的 `sweep` 是不同的东西：

| | `sweep` | `compare` |
|---|---|---|
| 每个点保留什么 | 只取末态汇总 | **完整轨迹** |
| 轴 | 变成 `parameter` | **保持内层的 `step`/`time`** |
| 产出 | 命中率曲线 | **N 条轨迹对齐播放** |
| 教学价值 | 看趋势 | 拖时间轴，同时看两种策略在这一步各自做了什么 |

**文档形状复用 `SimDocument`，没有新增顶层概念**：
`params.varyParam` 指定被对比的参数，`streams['variants']` 列出取值。

### 验证：一个好的教学反例

128B / 16B 块 / 2 路 → 4 组，地址 0、64、128、192 全落第 0 组。
访问序列 `0, 64, 0, 128, 64`：

```
[0] LRU 缺失(0/1)  │  FIFO 缺失(0/1)
[1] LRU 缺失(0/2)  │  FIFO 缺失(0/2)
[2] LRU 命中(1/3)  │  FIFO 命中(1/3)
[3] LRU 缺失(1/4)  │  FIFO 缺失(1/4)
[4] LRU 缺失(1/5)  │  FIFO 命中(2/5)   ← 分野在这一步
```

**FIFO 2 命中 > LRU 1 命中。** 原因在第 2 步：LRU 命中时刷新了时间戳，
导致第 3 步淘汰了 64；FIFO 不刷新，淘汰的是 0，于是第 4 步的 64 还在。

"LRU 未必更优"的经典反例 —— 正是 compare 原语该展示的东西。

TCP 那边同理：第 6 轮丢包时 **Reno 快恢复到 8，Tahoe 砍到 1**，两者分野一目了然。

组合内核照样过验收标准：确定性重放 ✅、DSL 唯一入口 ✅、换内核可插拔 ✅。
自检也带了一条特别的：**两道填同一个策略时轨迹必须完全相同**，
否则说明 `varyParam` 泄漏到了别的参数上。

## 二、L2 的真考题：让模型自己选原语

**关键设计**：如果直接把 `compare` schema 递给模型，等于人替它组装好了 —— 那还是 L1。

真正的 L2 是：**把全部 6 个工具一起给出去，`tool_choice: {type:'any'}` 强制调用但不指定调哪个**，
让模型自己判断这题该用单实验还是并排对比。

**而且必须混着考。** 只给对比题的话，模型全选 `compare` 也能满分，测不出它会不会判断。
所以题库一半对比题、一半单实验题。

### 结果

```
选对原语  36/36  100.0%
填对参数  36/36  100.0%   ← L2 真实通过率
延迟 中位 3.8s · P90 10.9s
```

12 道题（6 对比 + 6 单个）× 3 次，**没有一次选错形态**。
"分别采用…比较"→ compare，"采用 SRTF 调度"→ scheduler，判断得很干净。

对比题覆盖：LRU vs FIFO、直接映射 vs 4路、Reno vs Tahoe、FCFS vs SJF、
块大小 16B vs 32B、RR 时间片 2 vs 4 —— 六种不同的 `varyParam`。

## 三、挖出的问题：权威来源在哪

第一轮跑 3 次时是 **34/36（94.4%）**，一道题 3 次里错 2 次，报的是：

```
验证器拦下 kind: 未知的实验类型
```

但同一行又显示"选了 compare:cache"——**模型工具选对了，是 doc 里的 `kind` 字段填错了**。

根因跟上一轮的 `required` 是同一类：**端点也不强制 schema 的 `enum`**。
`kind: { enum: ['compare:cache'] }` 写了等于没写。

但这次的正解不是"加一条校验"，而是**换权威来源**：

> **多工具模式下，`doc.kind` 是冗余且不可靠的 —— 权威来源是被调用的工具名。**
> 工具名是 API 的路由结果，工具名↔kind 的映射由我们自己控制；
> 而 `doc.kind` 只是模型生成的一段文本。

**修**：`fillMultiTool` 直接用工具名覆盖 `doc.kind`，根本不去校验那个字段。
改完 36/36。

这条比"再加一条校验"更根本：**同一个信息有两个来源时，先问哪个是权威的，
而不是急着去校验不可靠的那个。**

## 四、三轮下来，同一族的坑

| 轮次 | 现象 | 根因 |
|---|---|---|
| L1 扩样本 | 模型省掉 `replacement` | 端点不强制 `required` |
| L1 扩样本 | 模型省掉 `entities: []` 被误拒 | 我的校验过严，没区分"缺值"和"缺空集合" |
| L2 | 模型把 `kind` 填错 | 端点不强制 `enum`；而且这个字段本就不该信 |

**共同点：JSON Schema 在这类端点上是"给模型的提示"，不是"给我们的保证"。**
凡是能从别处拿到权威值的字段（如 kind ← 工具名），就别让模型填；
必须让模型填的（如 replacement），落地校验必须自己做。

---

## 仍然不能说的

- **只测了一个模型**（MiniMax-M3）
- `compare` 只支持"变一个参数"，**没测多参数交叉对比**（如同时变相联度和替换策略）
- 没测**三个以上变体**并排（题库里都是两两对比）
- 没测**跨内核对比**（如 Cache 和 TLB 并排）—— 目前架构也不支持，需要时再说
- L2 只做了 `compare` 一个组合原语；`sweep` 还没进多工具池

## 复现

```bash
npm run test:l2         # compare 原语的正确性（不花钱）
npm run ai:l2           # AI 自选原语，跑一遍
npm run ai:l2 -- 3      # 每题 3 次
```
